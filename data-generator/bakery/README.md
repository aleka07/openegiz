# Виртуальная пекарня — генератор телеметрии и журнала событий

Сквозной сценарий курса, фаза 1. Симулятор изображает производственную линию
пекарни и кормит стек OpenEgiz **двумя разными потоками данных**:

1. **Телеметрия** — состояние оборудования (температура печи, нагрузка
   двигателя месильной машины…). Идёт через Eclipse Ditto и оседает в InfluxDB
   в measurement `mqtt_consumer`. Это «цифровой двойник» в узком смысле.
2. **Журнал событий процесса** (event log) — факты о партиях теста: «партия
   batch-0007 начала выпекаться в 10:42». Идёт **мимо Ditto** прямо в Telegraf
   и оседает в measurement `batch_events`. Это то, что читают pm4py и JaamSim.

Разделение принципиальное и его стоит проговорить на занятии: событие процесса
— утверждение о **партии**, а не о состоянии **устройства**. У него нет
двойника, которому можно поменять feature. Поэтому и путь другой.

## Топология линии

```
                 ┌──────────── бутылочное горлышко ────────────┐
                 │                                             │
  партия ──▶ mixer-1 ──▶ proofer-1 ──▶ oven-1 ──▶ packer-1 ──▶ готово
             замес       расстойка     выпечка    упаковка
             cap 1       cap 3         cap 1      cap 1
             ~8 мин      ~40 мин       ~25 мин    ~5 мин
             ────────    ─────────     ────────   ────────
             13 мин/шт   13 мин/шт     25 мин/шт  5 мин/шт   ◀ такт станции

  новая партия запускается каждые ~12 симулированных минут
```

Пропускная способность печи (одна партия за 25 минут) **вдвое ниже** темпа
запуска. Очередь перед печью растёт всю смену — это и есть узкое место, которое
на следующих занятиях должны самостоятельно найти pm4py и JaamSim. Расстойка
идёт 40 минут, но вмещает 3 партии, поэтому её такт — 13 мин/шт, и она узким
местом не является. Это специально: «самая долгая операция» и «бутылочное
горлышко» — не одно и то же.

## Двойники (Eclipse Ditto)

Namespace `bakery`, политика `default:basic_policy` (та же, что у остальных
двойников стенда).

| Thing ID | Features |
|---|---|
| `bakery:mixer-1` | `motor_load` (%), `dough_temp` (°C) |
| `bakery:proofer-1` | `temp` (°C), `humidity` (%) |
| `bakery:oven-1` | `temp` (°C) |
| `bakery:packer-1` | `throughput` (уп./мин) |
| `bakery:line` | `batches_started`, `batches_completed`, `wip` |

`bakery:line` — двойник линии целиком, а не железки: агрегированные счётчики
для бизнес-панели.

Температура печи не выдумана «шумом вокруг константы»: она стремится к 231 °C,
когда в печи есть партия, и к 175 °C в простое, с тепловой постоянной времени
4 симулированные минуты, плюс мгновенный провал на 18 °C при открытии дверцы.
Кривая температуры и журнал событий описывают одни и те же события — это нужно
для занятия по сопоставлению телеметрии и процесса.

## Установка

С ноутбука (rsync на хост + создание двойников в Ditto):

```bash
bash data-generator/bakery/install.sh              # rsync + двойники
bash data-generator/bakery/install.sh --no-twins   # только rsync
```

Скрипт кладёт файлы в `~/course/bakery/` на хосте. Пароль Ditto берётся на
хосте из `~/openegiz-deploy/secrets.values.yaml` — в репозитории и в git его
нет и быть не должно.

Пересоздать двойники отдельно (это же «сброс линии» — значения features
обнуляются):

```bash
ssh vpn-gx10-11 'bash ~/course/bakery/create_twins.sh'
```

## Запуск

На хосте, в venv курса (там уже стоит `paho-mqtt` — больше ничего не нужно):

```bash
# 20 партий, полная смена (~9 ч) за ~3 минуты реального времени
~/course/venv/bin/python ~/course/bakery/simulator.py \
    --batches 20 --speedup 200 --telemetry-interval 1.0

# «грязный» прогон: 15 % событий теряется, отдельный диапазон case_id
~/course/venv/bin/python ~/course/bakery/simulator.py \
    --batches 10 --speedup 400 --telemetry-interval 1.0 \
    --mode dirty --seed 99 --case-start 101

# посмотреть логику, ничего никуда не отправляя
~/course/venv/bin/python ~/course/bakery/simulator.py --batches 3 \
    --speedup 100000 --dry-run
```

Симулятор работает на переднем плане и печатает жизненный цикл каждой партии.
Останавливается сам, когда все партии готовы; `Ctrl+C` тоже безопасен.

### Ключи

| Ключ | Что делает |
|---|---|
| `--batches N` | сколько партий пропустить через линию (20) |
| `--speedup N` | сколько симулированных секунд проходит за одну реальную (1.0) |
| `--mode` | `normal` / `sparse` / `dirty` — см. ниже |
| `--seed N` | воспроизводимость: тот же seed → тот же прогон (42) |
| `--case-prefix` / `--case-start` | диапазон `case_id`; **разным датасетам — разные диапазоны** |
| `--telemetry-interval` | реальные секунды между публикациями телеметрии (2.0) |
| `--run-id` | метка прогона, пишется в каждое событие |
| `--mqtt-host` / `--mqtt-port` | брокер (`localhost:30511`) |
| `--dry-run`, `--verbose` | без публикации / печатать каждое MQTT-сообщение |

`--telemetry-interval` задаётся в **реальных** секундах, а один отсчёт при этом
покрывает `interval × speedup` симулированных секунд. При `--speedup 200`
берите `1.0`, иначе на кривой температуры печи будет 2–3 точки на выпечку и
корреляция станет неразличимой.

### Режимы качества данных

| Режим | Что происходит | Зачем |
|---|---|---|
| `normal` | все 8 событий на партию | эталонный лог, чистый DFG |
| `sparse` | на `proofer-1` и `packer-1` фиксируется только начало операции | длительность операции неизвестна — типичная ситуация, когда терминал стоит только на входе |
| `dirty` | каждое событие с вероятностью 15 % не записывается | «оператор забыл нажать кнопку»; DFG расползается в спагетти |

Симуляция самой линии от режима **не зависит** — теряются только записи в
журнале. Это важно: очереди и длительности остаются физически теми же, меняется
только то, что мы о них знаем.

## Куда попадают данные

```
                       ┌─ telemetry/<thingId> ─▶ Ditto ─▶ opentwins/# ─┐
simulator.py ──MQTT──▶ │  (Ditto Protocol)      (twin)                 ├─▶ Telegraf ─▶ InfluxDB
    :30511             └─ bakery/events ─────────────────────────────  ┘
                          (плоский JSON)                                      │
                                                                              ▼
                                                              Grafana «Bakery Line»
                                                              pm4py / JaamSim
```

| Поток | MQTT topic | Формат | Measurement | Теги |
|---|---|---|---|---|
| телеметрия | `telemetry/bakery:oven-1` | Ditto Protocol `modify /features` | `mqtt_consumer` | `thingId`, `topic`, `originator` |
| журнал | `bakery/events` | плоский JSON | `batch_events` | `case_id`, `activity`, `station`, `mode` |

Поля `batch_events`: `ts` (строка, **время процесса** — симулированное),
`run_id` (строка), `seq`, `queue_len`, `wip` (числа).

**Про два времени.** Точка в InfluxDB получает время **приёма** (реальное), а
поле `ts` содержит время **процесса** (симулированное). При `--speedup 200` они
расходятся: 9 часов смены прожимаются в 3 минуты реального времени. Process
mining обязан брать `ts` — иначе все длительности окажутся в 200 раз меньше.
Grafana же строит графики по времени приёма, поэтому в дашборде смена выглядит
как 3 минуты. Это не баг, а прямое следствие ускорения.

Ditto Protocol требует, чтобы в конверте namespace и имя разделялись `/`, а не
`:` — `bakery:oven-1` превращается в topic `bakery/oven-1/things/twin/commands/modify`.
Это самая частая ошибка при ручной публикации (подробности — в
`docs/install-log.md`, раздел про сквозной тест write-path).

## Проверка

```bash
# двойники существуют и обновляются
curl -s http://localhost:30528/api/twins/ | python3 -m json.tool

# журнал пригоден для process mining: DFG, узкое место, длины очередей
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
~/course/venv/bin/python ~/course/bakery/check_log.py --mode normal --range=-6h
~/course/venv/bin/python ~/course/bakery/check_log.py --mode dirty  --range=-6h
```

`check_log.py` читает `batch_events` прямо из InfluxDB, собирает лог pm4py и
печатает DFG вместе со средними длительностями рёбер. На чистом прогоне ребро
`ProofingDone → BakingStarted` (ожидание перед печью) должно доминировать.

Дашборд: Grafana → папка **OpenEgiz** → **Bakery Line**
(`/d/openegiz-bakery-line/bakery-line`).
