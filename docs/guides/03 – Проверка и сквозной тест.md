# 03. Проверка и сквозной тест телеметрии

Платформа поднялась — 14 подов `Running`. Это ещё ничего не доказывает: поды могут крутиться и при полностью мёртвом пайплайне. В этом гайде мы сначала проверяем каждый сервис по отдельности, а потом прогоняем **одно сообщение через всю цепочку** и смотрим, что оно доехало до Grafana.

Всё ниже проверено на живом кластере. Ни на одном шаге не потребовалось ничего чинить.

**MongoDB и что Ditto в неё реально пишет:**

```bash
kubectl exec -n opentwins opentwins-mongodb-0 -- mongosh --quiet --eval 'db.adminCommand({ping:1})'
# {"ok":1}
# базы: admin, config, ditto, local   <- наличие 'ditto' и есть доказательство
```

**Connections Ditto.** Здесь есть неприятный сюрприз: `GET /api/2/connections` возвращает `[]`, даже когда connections существуют и работают. Это известная особенность Ditto (`retrieveAllConnections` не обходит шардированные акторы). Не пугайтесь и не идите чинить. Реальный статус — через devops piggyback API:

```bash
curl -s -u devops:$DEVOPS_PW -X POST \
  "http://localhost:30525/devops/piggyback/connectivity?timeout=10s" \
  -H "Content-Type: application/json" \
  -d '{"targetActorSelection":"/system/sharding/connection","headers":{"aggregate":false},
       "piggybackCommand":{"type":"connectivity.commands:retrieveConnection",
                           "connectionId":"mosquitto-source-connection"}}'
```

Должны быть открыты обе:

| Connection | Направление | Что делает |
|---|---|---|
| `mosquitto-source-connection` | in | подписан на `telemetry/#`, authCtx `nginx:ditto`, **payload mapper отсутствует** |
| `mosquitto-target-connection` | out | публикует в `opentwins/{{topic:channel}}/{{topic:criterion}}/{{thing:namespace}}/{{thing:name}}` |

Connections ровно две — и это правильно. Третья (Hono) описана в `values.yaml`, но `hono.enabled: false`, поэтому пропускается.

# Сквозной тест: одно сообщение через всю цепочку

```text
MQTT publish → source connection → состояние двойника → target connection
            → mosquitto opentwins/# → Telegraf → InfluxDB2 → Grafana
```

## Контракт: топик и конверт

Две вещи должны сойтись — **топик MQTT** и **конверт сообщения**.

**Топик:** `telemetry/<thingId>`, например `telemetry/test:winterschool-1`.
Source connection подписан на `telemetry/#`. При этом `<thingId>` в топике — **чисто косметика**: Ditto маршрутизирует по полю `topic` *внутри* payload, а не по MQTT-топику. Держать их согласованными — соглашение, а не требование.

**Payload:** сырой конверт **Ditto Protocol**. Payload mapper на source connection не настроен, поэтому всё, что не является валидным Ditto Protocol, просто выбрасывается. Минимальная рабочая форма:

```json
{
  "topic": "test/winterschool-1/things/twin/commands/modify",
  "path": "/features",
  "value": {
    "temperature": {
      "properties": {
        "value": 42.5,
        "timestamp": "2026-08-07T09:04:58Z"
      }
    }
  }
}
```

> **Самая частая ошибка в одном предложении.** В `thingId` разделитель — двоеточие, в `topic` конверта — слэш: `test:winterschool-1` → `test/winterschool-1`. Формат `topic` целиком: `<namespace>/<name>/things/twin/commands/modify`.

**Двойник должен существовать заранее**, вместе с политикой. Команда `modify` по этому пути **не создаёт** несуществующий Thing.

Ровно такой конверт собирает `examples/oven/data_generator.py` (`build_ditto_message()` / `MqttPublisher.topic`), так что генераторы из репозитория можно брать как есть.

## Шаг 1. Создаём тестовый двойник

Политику берём ту, что создал post-install hook — `default:basic_policy` (subject `nginx:ditto`, полные READ/WRITE). Свою выдумывать не надо.

```bash
curl -s -u ditto:$DITTO_PW -X PUT \
  -H "Content-Type: application/json" \
  http://localhost:30525/api/2/things/test:winterschool-1 \
  -d '{"policyId":"default:basic_policy",
       "attributes":{"purpose":"e2e-write-path-test"},
       "features":{"temperature":{"properties":{"value":0}}}}'
# -> HTTP 201
```

Двойник `test:winterschool-1` намеренно оставлен на стенде — он полезен для курса.

## Шаг 2. Публикуем

`mosquitto_pub` и `mosquitto_sub` уже лежат внутри пода брокера (`/usr/bin/`), ставить клиент на хост не нужно:

```bash
kubectl exec -n opentwins deploy/opentwins-mosquitto -c mosquitto -- \
  mosquitto_pub -h localhost -p 1883 \
    -t 'telemetry/test:winterschool-1' \
    -m '{"topic":"test/winterschool-1/things/twin/commands/modify",
         "path":"/features",
         "value":{"temperature":{"properties":{"value":42.5,
                  "timestamp":"2026-08-07T09:04:58Z"}}}}'
```

С ноутбука в той же LAN то же самое работает против `gx10-11:30511` — именно так и делают скрипты из `examples/`.

## Шаг 3. Что должно произойти на каждом участке

### A. MQTT → состояние двойника

```bash
curl -s -u ditto:$DITTO_PW http://localhost:30525/api/2/things/test:winterschool-1
```

```json
{"thingId":"test:winterschool-1","policyId":"default:basic_policy",
 "attributes":{"purpose":"e2e-write-path-test"},
 "features":{"temperature":{"properties":{"value":42.5,"timestamp":"2026-08-07T09:04:58Z"}}}}
```

Значение уехало с посеянного `0` на `42.5`. ✅

### B. Ditto → mosquitto `opentwins/#`

Запускаем подписку **до** публикации:

```bash
kubectl exec -n opentwins deploy/opentwins-mosquitto -c mosquitto -- \
  mosquitto_sub -h localhost -p 1883 -t 'opentwins/#' -v
```

На топике `opentwins/twin/events/test/winterschool-1` прилетает:

```json
{"topic":"test/winterschool-1/things/twin/events/modified",
 "headers":{"ditto-originator":"nginx:ditto","response-required":false,"version":2,
            "requested-acks":[],"content-type":"application/json"},
 "path":"/features",
 "value":{"temperature":{"properties":{"value":42.5,"timestamp":"2026-08-07T09:04:58Z"}}},
 "extra":{"thingId":"test:winterschool-1"},
 "revision":2,"timestamp":"2026-08-07T09:05:00.491024520Z"}
```

Видно, как раскрылся шаблон топика: `channel=twin`, `criterion=events`, `namespace=test`, `name=winterschool-1`.

Поле `extra.thingId` здесь **несущее**: target connection добавляет его через `extraFields`, и именно его Telegraf использует как тег в InfluxDB. Уберёте — сломается запись.

### C. Telegraf → InfluxDB

```bash
kubectl logs -n opentwins deploy/opentwins-telegraf --tail=20
```

В момент публикации:

```text
D! [parsers.json_v2::mqtt_consumer] the path "extra.attributes._parents" doesn't exist
D! [parsers.json_v2::mqtt_consumer] the path "headers.correlation-id" doesn't exist
D! [parsers.json_v2::mqtt_consumer] the path "extra.features.idSimulationRun.properties.value" doesn't exist
D! [outputs.influxdb_v2] Wrote batch of 1 metrics in 4.652741ms
```

**Эти три `doesn't exist` — безобидный шум, гоняться за ними не надо.** Все три пути объявлены в конфиге Telegraf как `optional = true` и появляются для любого двойника без родительской иерархии и без id симуляции, то есть для большинства. В поставляемом конфиге включён `debug = true`, отсюда и уровень D!.

Проверяем данные в InfluxDB напрямую:

```bash
TOKEN=$(kubectl get secret -n opentwins opentwins-influxdb2-auth \
          -o jsonpath='{.data.admin-token}' | base64 -d)

kubectl exec -n opentwins opentwins-influxdb2-0 -- \
  influx query --org opentwins --token "$TOKEN" --raw '
    from(bucket: "default")
      |> range(start: -1h)
      |> filter(fn: (r) => r.thingId == "test:winterschool-1"
                        and r._field == "value_temperature_properties_value")
      |> keep(columns: ["_time","_value","thingId"])'
```

```text
,result,table,_time,_value,thingId
,,0,2026-08-07T09:04:43.432808186Z,0,test:winterschool-1     <- это PUT, которым создали двойник
,,0,2026-08-07T09:05:00.508938666Z,42.5,test:winterschool-1
,,0,2026-08-07T09:05:47.349029281Z,43.7,test:winterschool-1
,,0,2026-08-07T09:05:53.541139617Z,46.1,test:winterschool-1
```

Обратите внимание на первую строку: это **REST-запрос**, а не MQTT. Ditto порождает twin event на любое изменение состояния независимо от источника, поэтому HTTP API — тоже полноценный путь записи в InfluxDB. Хороший демонстрационный момент для курса: источник правды — двойник, а не транспорт.

Как называются поля: измерение `mqtt_consumer`, имена полей — уплощённое значение события, `value_temperature_properties_value`. Полный набор тегов: `thingId`, `topic`, `originator=nginx:ditto`, `host=telegraf-polling-service` и `correlationId`, когда он есть. Эти имена вам понадобятся во Flux-запросах Grafana.

### D. Grafana читает

Проверять надо не «datasource в списке есть», а реальный запрос через её же прокси:

```bash
curl -s -u admin:$GRAFANA_PW -X POST http://localhost:30718/api/ds/query \
  -H 'Content-Type: application/json' \
  -d '{"queries":[{"refId":"A","datasource":{"type":"influxdb","uid":"P4528D75AB74BE2EA"},
       "query":"from(bucket: \"default\") |> range(start: -1h) |> filter(...)"}],
       "from":"now-1h","to":"now"}'
```

```json
"status":200,
"data":{"values":[[1786093483432,1786093500508,1786093547349,1786093550439,1786093553541],
                  [0,42.5,43.7,44.9,46.1]]}
```

Ряд вернулся с правильными типами (`time` + `float64`). Цепочка замкнулась. ✅

## Что запомнить (и вынести в материалы курса)

- **`thingId` через `:`, топик конверта через `/`.** `test:winterschool-1` → `test/winterschool-1`.
- **Payload mapper'а нет.** Кривой payload выбрасывается **молча**: publisher ничего не узнает (QoS 0, reply target не используется). Способ отладки: подписаться на `opentwins/#` и смотреть на *отсутствие* события.
- **Двойник должен существовать заранее**, с политикой. Используйте `default:basic_policy`.
- **Сквозная задержка ~10 секунд**, и почти вся она — `flush_interval = "10s"` у Telegraf. Это конфигурация, а не проблема, но человека, который обновляет Grafana сразу после публикации, она гарантированно запутает.
- **`doesn't exist` в логах Telegraf — ожидаемый шум** от `optional = true` путей.
