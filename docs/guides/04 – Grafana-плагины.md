# 04. Grafana-плагины: вендоринг, ребрендинг и офлайн-старт

Grafana в OpenEgiz — это не только дашборды. Через плагин `ertis-opentwins-app` (у нас он подписан **OpenEgiz**) делается вся работа с двойниками: создание, просмотр, политики. Второй плагин, `ertis-unity-panel`, рисует Unity-сцену в панели.

Оба плагина фронтенд-only — никаких бинарников бэкенда, поэтому они просто распаковываются в `/grafana-storage/plugins` и грузятся неподписанными через `allow_loading_unsigned_plugins`.

Этот гайд — про то, откуда они берутся, как их переклеить под OpenEgiz заново и почему Grafana теперь стартует даже без интернета.

Полные технические детали: [notes-rebrand-plugins.md](../notes-rebrand-plugins.md) и [vendor/grafana-plugins/README.md](../../vendor/grafana-plugins/README.md).

## Как было и почему так нельзя

Апстримный `values.yaml` на **каждом старте пода** качал оба zip из GitHub-релизов ertis-research:

```sh
wget ... https://github.com/ertis-research/opentwins-in-grafana/releases/download/latest/ertis-opentwins-app.zip
wget ... https://github.com/ertis-research/grafana-panel-unity/releases/download/latest/ertis-unity-panel.zip
```

Три проблемы, и все три реальные:

1. **Рантайм-зависимость от чужого GitHub.** Нет сети или релиз удалили — Grafana не стартует. И это ровно та ситуация, которая случается после отключения питания, когда сеть поднимается позже машины.
2. **Первый URL — редирект.** Репозиторий `opentwins-in-grafana` переименован в `grafana-app-opentwins`. Работает только пока GitHub держит редирект живым — и сломается в тот день, когда кто-то создаст новый репозиторий со старым именем.
3. **Тег `latest` плавающий.** Апстрим может подменить артефакт в любой момент, и кластер молча подхватит другую сборку.

## Как стало

Оба zip лежат в репозитории, в [vendor/grafana-plugins/](../../vendor/grafana-plugins/):

| Путь | Что это |
|---|---|
| `ertis-opentwins-app.zip` | пропатченный app-плагин — его тянет init-контейнер |
| `ertis-unity-panel.zip` | пропатченный panel-плагин |
| `upstream/*.zip` | немодифицированные оригиналы (для провенанса и диффов) |
| `patch-branding.py` | пересобирает пропатченные zip из `upstream/` |

Init-контейнер в `values.yaml` теперь ходит по нашим raw-ссылкам:

```diff
-wget ... https://github.com/ertis-research/opentwins-in-grafana/releases/download/latest/ertis-opentwins-app.zip
+wget ... https://raw.githubusercontent.com/aleka07/openegiz/main/vendor/grafana-plugins/ertis-opentwins-app.zip
```

`vendor/` добавлен в `.helmignore` — zip'ы качаются по HTTP при старте пода, встраивать их в tarball чарта незачем.

> ⚠️ **Эти ссылки отдают 404, пока `vendor/` не запушен в `main` публичного `aleka07/openegiz`.** Если после свежего клона Grafana не поднимается с ошибкой скачивания плагинов — сначала проверьте, что каталог реально доступен на raw.githubusercontent.com, и только потом ищите баг.

## Офлайн-старт: кэш на PVC

После отключения питания всей стойки выяснилась ещё одна вещь: старый скрипт init-контейнера работал с `set -e`, то есть **любой неудачный `wget` = Grafana вообще не стартует**. Нет сети — нет Grafana, хотя плагины уже лежат распакованными на диске.

Текущий скрипт (в `values.yaml`, `grafana.extraInitContainers[0]`) работает по трём ветвям:

```sh
# без `set -e`: неудачная закачка НЕ должна блокировать старт, если
# на PVC уже лежит распакованная копия плагина
mkdir -p /grafana-storage/plugins
cd /grafana-storage/plugins
for P in ertis-opentwins-app ertis-unity-panel; do
  if wget --no-cache --no-check-certificate -O "$P.zip" "https://raw.githubusercontent.com/.../$P.zip"; then
    unzip -o "$P.zip" && rm "$P.zip"          # 1. сеть есть -> свежая версия побеждает
  elif [ -d "$P" ]; then
    echo "WARN: download of $P failed, keeping cached copy on PVC"
    rm -f "$P.zip"                            # 2. сети нет, но копия есть -> живём
  else
    echo "ERROR: $P unavailable: download failed and no cached copy" >&2
    exit 1                                    # 3. ни того, ни другого -> честно падаем
  fi
done
```

Фоллбэк проверен не чтением кода, а запуском: скрипт прогнали в busybox с `--network none` и подложенным фейковым каталогом плагина — для закэшированного получили `WARN ... keeping cached copy` и продолжение, для незакэшированного — жёсткий ERROR. В проде обе копии оказываются на PVC после первого успешного старта, поэтому полностью офлайновая загрузка проходит.

## Грабля Grafana, не связанная с плагинами: crashloop при апгрейде

Всплыла ровно тогда, когда первый раз делали `helm upgrade` ради вендоренных плагинов. Новый под встал в `Init:Error`:

```text
chown: /var/lib/grafana/pdf: Permission denied
```

Старый под при этом продолжал работать — простоя не было.

**Причина.** Init-контейнер `init-chown-data` из чарта Grafana запускается от root, но чарт сбрасывает все capabilities кроме `CHOWN`. На **свежем** PVC внутрь рекурсировать некуда, поэтому первая установка проходит. Потом Grafana в рантайме создаёт `csv/`, `pdf/`, `png/` с правами 700 и владельцем uid 472 — а чтобы зайти внутрь чужого каталога с правами 700, нужен `CAP_DAC_OVERRIDE`, который сброшен. Итог: **каждый апгрейд после первой установки** ломается в Init.

**Фикс** (в `values.yaml`, с комментарием на месте):

```yaml
grafana:
  initChownData:
    enabled: false
```

Права и так корректны — их обеспечивает `fsGroup: 472`, так что весь этот chown-проход здесь просто лишний. После правки апгрейд сошёлся за 20 секунд.

## Как переклеить брендинг заново

Один скрипт, запускается на любой машине с Python 3:

```bash
cd vendor/grafana-plugins
python3 patch-branding.py            # пересобрать оба zip из upstream/
python3 patch-branding.py --check    # проверить, что лежащие zip совпадают со свежим прогоном
```

Скрипт читает `openegiz_logo_centered.svg` из корня репозитория и пересобирает архивы запись за записью, сохраняя имена, порядок, таймстампы и режимы — распакованная init-контейнером структура остаётся идентичной апстримной.

**Ключевое свойство: каждая замена требует ровно одного совпадения и падает иначе.** Если апстрим переформатирует любую из этих строк, скрипт громко умрёт вместо того, чтобы молча выпустить наполовину переклеенный плагин. Первая попытка так и упала — на разных переводах строк в двух README (у app-плагина CRLF, у unity LF), и это была ровно та защита, ради которой всё писалось.

### Что патчится

App-плагин — 7 записей из 27:

| Файл | Изменение |
|---|---|
| `plugin.json` | `"name": "OpenTwins"` → `"OpenEgiz"` |
| `img/logo.svg` | логотип OpenEgiz |
| `6824e6a2fada2cf50285.svg` | тот же логотип — webpack-хешированная копия, которую `396.js` рисует в шапке приложения |
| `README.md` | H1, вводное предложение, заметка про «OpenTwins middleware» |
| `202.js` | текст алерта на странице настроек плагина |
| `396.js` | `<h1>` в шапке и `alt` у логотипа |
| `module.js` | пересчитанные SRI-дайджесты чанков 202 и 396 |

Unity-панель — 1 запись из 13: только `README.md`.

### Почему Unity-панели оставили её логотип

Первый проход заменил и его, второй — вернул обратно. У этой панели вообще нет брендинга OpenTwins: `name` там `"Unity"`, описание про Unity WebGL, иконка — марка движка Unity. Эта иконка **функциональна**: по ней панель находят в списке из нескольких десятков. Замена её на вордмарк OpenEgiz с соотношением 4.2:1 ничего не ребрендила, зато делала панель труднее опознаваемой.

### Самое хитрое место: SRI

`module.js` пиннит sha256-дайджест для каждого лениво загружаемого чанка:

```js
sriHashes = { 126: "sha256-…", 202: "sha256-…", 396: "sha256-…" }
```

Обе оставшиеся UI-строки живут как раз в `202.js` и `396.js`. Правишь там хоть один байт — дайджест не сходится, Grafana отказывается грузить чанк, плагин рисует пустую страницу.

Формат — `"sha256-" + base64(sha256(байты_чанка))`. Прежде чем что-либо трогать, метод **проверили на нетронутом апстриме**: пересчёт всех трёх дайджестов из оригинальных чанков воспроизвёл значения, которые апстрим запиннил. Вот это и делает пересчёт достоверным, а не догадкой. `module.js` собственного дайджеста не несёт, поэтому переписывается на месте безопасно.

Патчер после записи перечитывает `module.js` и проверяет каждый дайджест против его чанка — испорченная перезапись физически не доедет до продакшена.

### Что переименовывать НЕЛЬЗЯ

Выглядит как брендинг, но является несущей конструкцией:

| Строка | Где | Почему |
|---|---|---|
| `ertis-opentwins-app`, `ertis-unity-panel` | `id` в `plugin.json`, public path в `module.js`, plugin-proxy в `396.js` | Grafana раздаёт ассеты из `public/plugins/<id>/` и роутит `api/plugin-proxy/<id>/` |
| `webpackChunkertis_opentwins_app` | все чанки | глобал webpack-рантайма; переименование в одном чанке ломает загрузку |
| `opentwins.agents/name`, `opentwins.agents/twins` | `396.js` | ключи k8s-лейблов, которые плагин пишет на Deployment'ы/CronJob'ы и потом читает обратно |

Отсюда честный вывод: **ребрендинг косметически полный, но структурно неглубокий.** Пользователь, открывший devtools или `kubectl get deploy --show-labels`, всё ещё увидит OpenTwins. Изменить это может только форк плагина на уровне исходников — с обязательством дальше его сопровождать. До зимней школы это не рекомендуется.

### Атрибуция

`info.author` (`ERTIS`), ссылки на апстрим и файл `LICENSE` оставлены нетронутыми. Плагины — работа ERTIS под Apache-2.0; снять атрибуцию и поставить своё имя это и плохая практика, и нарушение лицензии.

Текст ссылок, называющий апстримный проект, тоже сохранён — переименовать `[OpenTwins](github.com/ertis-research/opentwins)` в «OpenEgiz» значило бы просто сделать ссылку неверной. Поэтому README app-плагина читается так:

> The **OpenEgiz App Plugin** serves as the central frontend interface for the OpenEgiz platform, built on [OpenTwins](https://github.com/ertis-research/opentwins).

## Проверка на живом кластере

```bash
# плагины распакованы
kubectl exec -n opentwins deploy/opentwins-grafana -c grafana -- ls -1 /var/lib/grafana/plugins

# Grafana видит плагин под новым именем
curl -s -u admin:admin http://localhost:30718/api/plugins/ertis-opentwins-app/settings
# -> name: OpenEgiz, enabled: true, pinned: true

# init-контейнер тянул именно наши копии
kubectl logs -n opentwins deploy/opentwins-grafana -c install-opentwins-plugins
```

## Известные хвосты

- **Логотип нечитаем в маленьком слоте.** Логотип OpenEgiz — вордмарк примерно 4.2:1. Даже плотно обрезанный, в 24-пиксельном слоте навигации (`logos.small`) он не читается. Правильное решение — отдельный вариант «только знак» для `logos.small` и полный вордмарк для `logos.large`. Это дизайнерское решение, не код.
- **SVG логотипа использует `<text>` с `font-family: Inter`, а не обведённые контуры.** В Grafana рендерится корректно (Inter — её UI-шрифт), но файл не самодостаточен. Перевод текста в кривые сделал бы его устойчивым везде.
- **Source maps (`*.js.map`)** всё ещё содержат исходники до ребрендинга и слегка разъехались по колонкам (`OpenTwins` — 9 символов, `OpenEgiz` — 8). SRI их не проверяет, доступны только через devtools — оставлены как есть.
- **При обновлении апстрима:** кладём новые zip в `upstream/`, гоняем `patch-branding.py` и ждём, что он упадёт, если какая-то из закреплённых строк сдвинулась. Имя `6824e6a2fada2cf50285.svg` тоже изменится (это webpack-хеш) — его надо заново вычитать из листинга архива, а не предполагать.
