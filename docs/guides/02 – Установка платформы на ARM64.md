# 02. Установка платформы на ARM64

Здесь мы ставим сам чарт OpenEgiz на кластер, собранный в гайде [01](01%20–%20Подготовка%20машины,%20k3s%20и%20Helm.md).

Три правки под ARM64 и стабильность **уже лежат в репозитории** — отдельно их применять не надо. Но каждую из них нужно понимать, потому что две из трёх при неаккуратном обращении молча ломают установку. Ниже сначала действия, потом объяснения.

Хронология с ошибками, диагностикой и логами — [install-log.md](../install-log.md), раздел «First deploy on k3s».

## Предпосылки

- k3s и Helm стоят, `kubectl get nodes` показывает `Ready`
- есть исходящий интернет (образы + плагины Grafana тянутся при первом старте)
- на хосте есть Docker — он нужен один раз, чтобы собрать образ extended API

## Шаг 1. Собрать образ Ditto Extended API

**Это надо сделать ДО `helm install`.** Образ существует только в локальном хранилище containerd — если его нет, под встанет в `ImagePullBackOff`, потому что тянуть его неоткуда.

Всё автоматизировано одним скриптом, запускать его надо **на самой arm64-машине**, не на ноутбуке:

```bash
cd ~/openegiz-deploy/chart      # или где у вас лежит репозиторий на хосте
bash rebuild/extended-api/build.sh
```

Что скрипт делает по шагам:

1. клонирует `ertis-research/extended-api-for-eclipse-ditto` на закреплённый коммит `b49663dea326854a2323423eaeab7e7f54d325a7` и проверяет, что HEAD совпал;
2. кладёт наш `Dockerfile` (отличается от апстримного `Dockerfile.sample` ровно двумя строками, см. ниже);
3. собирает нативно под arm64, без QEMU: `openegiz/ditto-extended-api:arm64-b49663d` + `:latest`;
4. прогоняет smoke-тест;
5. экспортирует в `~/openegiz-build/ditto-extended-api-arm64.tar.gz` (142 MB);
6. импортирует в containerd кластера: `sudo k3s ctr images import -`.

Проверяем, что образ действительно в кластере:

```bash
sudo k3s ctr images ls -q | grep extended-api
```

```text
docker.io/openegiz/ditto-extended-api:arm64-b49663d
docker.io/openegiz/ditto-extended-api:latest
```

Что считать нормальным в smoke-тесте: приложение печатает `Extended API for Eclipse Ditto listening`, потом ругается `MongoRuntimeError: Unable to parse IP_MONGODB:PORT_MONGODB` и **не падает**. Это апстримный плейсхолдер в образе, реальный адрес Mongo подставляется чартом при деплое. `curl http://localhost:18080/` отдаёт `404` — тоже правильный ответ: роут `/` не объявлен, а 404 вместо connection refused доказывает, что express слушает.

Подробный разбор сборки, включая найденный баг апстрима — [notes-extended-api-build.md](../notes-extended-api-build.md).

## Шаг 2. Доставить чарт на хост

Если репозиторий редактируется на ноутбуке, а ставится на gx10-11:

```bash
ssh gx10-11 'mkdir -p ~/openegiz-deploy/chart'
rsync -a --delete --exclude .git \
  "/путь/к/openegiz/" gx10-11:~/openegiz-deploy/chart/
```

`mkdir` перед rsync обязателен: rsync не создаёт отсутствующую директорию-прародителя и падает с `mkdir ... failed: No such file or directory (2)`.

Сабчарты вендорены в `charts/`, поэтому `helm dependency build` запускать **не нужно** и ни один внешний репозиторий не опрашивается. Проверить, что чарт рендерится:

```bash
cd ~/openegiz-deploy/chart
helm template opentwins . -n opentwins > /tmp/rendered.yaml
```

Должно отработать без stderr (у нас — 4847 строк).

## Шаг 3. Установка

```bash
make install
```

Или то же самое руками:

```bash
helm install opentwins . -n opentwins --create-namespace --wait --timeout=15m
```

> **Имя релиза обязано быть `opentwins`.** Несколько значений в чарте ссылаются на имена, производные от имени релиза (например, конфигмапа `opentwins-telegraf-real-config`). Переименование релиза — отдельная задача ребрендинга, а не «поменять одно слово в команде». Makefile прибивает имя гвоздями именно поэтому.

Смотрим, как поднимается, во втором терминале:

```bash
watch -n 2 kubectl get pods -n opentwins
```

На gx10-11 `helm install` вернул `deployed` за **57 секунд**, 14/14 подов `Running`. Таймлайн:

| t | что происходит |
|---|---|
| 0 с | старт `helm install` |
| ~25 с | все 5 JVM-сервисов Ditto `Running`, но `0/1`; nginx ждёт в `Init:0/1` |
| ~50 с | все 5 сервисов `1/1 Ready`, кластер Akka собрался, nginx поднялся |
| 57 с | post-install hook прошёл, helm вернул `deployed` |

Меньше минуты — это быстро (обычно ждут 5–15), но здесь 20 CPU и 121 GB RAM. Проверки из гайда [03](03%20–%20Проверка%20и%20сквозной%20тест.md) подтверждают, что всё действительно работает.

## Шаг 4. Проверить, что встало

```bash
make status        # kubectl get pods -n opentwins
make endpoints     # список сервисов с IP и портами
```

Ожидаем 14 подов `Running`. Проверки по каждому сервису — гайд [03](03%20–%20Проверка%20и%20сквозной%20тест.md).

# Три правки: что именно поправлено и зачем

Всё это уже в `values.yaml` и в комментариях внутри него. Раздел нужен, чтобы вы не откатили что-то из этого «за ненадобностью».

## Правка 1. Extended API — локальный образ вместо апстримного

**Проблема.** `ertis/ditto-extended-api` опубликован только под amd64 — все четыре тега (`latest`, `1.0.2`, `1.0.1`, `1.0.0`). На aarch64 пулл падает с `no match for platform in manifest`.

**Решение.** Пересобрали из исходников нативно на самой машине (шаг 1 выше). В `values.yaml`:

```yaml
extendedAPI:
  image:
    repository: openegiz/ditto-extended-api
    tag: arm64-b49663d
    pullPolicy: IfNotPresent
```

Плюс в `templates/extended-api/deploy.yaml` захардкоженный `imagePullPolicy: Always` сделан настраиваемым (заодно убран дубликат ключа, оставшийся от апстрима).

**Почему `IfNotPresent` критичен.** Образа нет ни в одном реестре. При `Always` Kubernetes на каждом старте пойдёт в Docker Hub, получит 404 и встанет в `ImagePullBackOff` — при полностью корректно импортированном локальном образе. Для тега `:latest` политика по умолчанию как раз `Always`, поэтому мы ссылаемся на неизменяемый `arm64-b49663d`, а не на `latest`.

**Почему образ не выложен в реестр.** У апстрим-репозитория нет файла лицензии. Раз права на распространение не заданы явно — образ остаётся локальным. Воспроизводимость обеспечивается не реестром, а закреплённым коммитом и `rebuild/extended-api/`.

**Найденный по дороге баг апстрима.** `Dockerfile.sample` делает `COPY package*.json ./` — без `yarn.lock`. Yarn пишет `info No lockfile found` и заново резолвит все `^`-диапазоны, то есть две сборки с одного коммита дают разные деревья зависимостей. Наш Dockerfile отличается ровно этим:

```diff
-COPY package*.json ./
-RUN yarn install
+COPY package*.json yarn.lock ./
+RUN yarn install --frozen-lockfile
```

**Оговорка про одну ноду.** Импорт коснулся containerd только gx10-11. Появится вторая нода — надо либо импортировать тарбол и туда, либо прибить под к этой ноде.

## Правка 2. MongoDB — обычный StatefulSet вместо bitnami-чарта

**Проблема.** Чарт тянет bitnami `mongodb` 13.18.5 с образом `bitnamilegacy/mongodb:6.0.10-debian-11-r8`. Просканированы все 2350 тегов этого репозитория — **ни одного с arm64**. Подменить внутри bitnami-чарта только образ тоже нельзя: его шаблоны вызывают `/opt/bitnami/scripts/*`, которых в официальном образе нет.

**Решение.** Bitnami-сабчарт выключен (`mongodb.enabled: false`), вместо него — `templates/mongodb-plain.yaml`: Service + StatefulSet на 1 реплику, официальный `mongo:6.0` (мультиарх), `--bind_ip_all`, probes через `mongosh`, PVC на `local-path`.

```yaml
plainMongodb:
  enabled: true
  image: mongo:6.0
  service:
    type: NodePort
    port: 27017
    nodePort: 30717
  persistence:
    storageClass: local-path
    size: 8Gi
```

**Как сохранена совместимость.** Новый Service именуется тем же хелпером `opentwins.mongodb.fullname`, что и раньше, и слушает тот же 27017. Поэтому секрет с connection-строками Ditto, extended API и (выключенный) Hono продолжают резолвить тот же `opentwins-mongodb:27017` — ни одного downstream-файла править не пришлось. Проверено диффом `helm template` против базовой версии.

Три вещи, за которые можно случайно зацепиться:

- **Не включайте оба разом.** `mongodb.enabled: true` и `plainMongodb.enabled: true` одновременно — два Service с одинаковым именем, установка падает. Гарда в шаблонах нет.
- **Данные не мигрируют.** У bitnami был PVC `opentwins-mongodb`, у StatefulSet — `data-opentwins-mongodb-0`. На чистой установке всё равно, на существующей старый том осиротеет.
- **Блок `mongodb:` в values.yaml трогать нельзя целиком** — в нём остаётся `nameOverride: mongodb`, который читает тот самый хелпер имени.

> ⚠️ **Незакрытая дыра, унаследованная от апстрима.** MongoDB работает без аутентификации и опубликована на NodePort 30717. Это поведение перенесено один в один из bitnami-конфига, но его надо закрыть: `plainMongodb.service.type: ClusterIP` — внутри чарта NodePort никому не нужен, он только для внешних инструментов.

Полный разбор — [notes-mongodb-arm64.md](../notes-mongodb-arm64.md).

## Правка 3. JVM Ditto — явный `-XX:MaxRAM`

Самая неочевидная из трёх. Без неё **все пять сервисов Ditto уходят в CrashLoopBackOff и установка не проходит вообще**.

**Симптом.** Логи контейнера обрываются на середине без единого java-исключения, последняя строка всегда одна и та же (`SBR will be automatically enabled after <PT1H>`). `kubectl describe` объясняет:

```text
Last State:  Terminated
  Reason:    OOMKilled
  Exit Code: 137
  Started:   13:27:44
  Finished:  13:27:45
```

Убит через секунду после старта. Все пять — одинаково.

**Ложный след.** Логично предположить, что heap не влезает в 1 GiB лимита. Подняли лимит до 2 GiB всем пяти — **всё равно OOMKilled**. Лимит удвоился, поведение не изменилось: значит, JVM про лимит вообще не знает.

**Настоящая причина.** Проб внутри реального образа показал:

```text
/sys/fs/cgroup/memory.max = 2147483648      <- ядро отдаёт лимит корректно, cgroup v2
UseContainerSupport      = true             <- поддержка контейнеров включена
MaxRAM                   = 130596184064     <- а JVM видит 121 GiB ХОСТА
MaxHeapSize              = 78383153152      <- и решает взять heap на 73 GiB
```

JDK 17.0.8.1 (aarch64, зашит в `eclipse/ditto:3.3.7`) на ядре `6.17.0-1026-nvidia` не определяет лимит cgroup. Дальше он применяет к 121 GiB `-XX:MaxRAMPercentage=60`, получает 73 GiB, а `InitialRAMPercentage=60` заставляет закоммитить этот heap сразу — ядро убивает контейнер через секунду.

**Фикс.** Задать JVM явную базу для расчёта процентов:

```yaml
ditto:
  global:
    jvmOptions: >
      ...
      -XX:MaxRAM=2147483648
```

После этого:

```text
MaxRAM      = 2147483648   {command line}
MaxHeapSize = 1289748480   {ergonomic}    <- 1.23 GiB, ровно 60% от 2 GiB
```

Плюс `resources.memoryMi: 2048` на всех пяти сервисах (апстрим ставит 1024).

> **Две ловушки, которые стоят отдельного абзаца.**
>
> **Ключи в values.yaml непоследовательно именованы.** Четыре сервиса пишутся в нижнем регистре (`things`, `policies`, `connectivity`, `gateway`), а пятый — **`thingsSearch`**. Первая попытка использовала `thingssearch:`, и Helm **молча проигнорировал** этот блок: значения, не совпадающие ни с одним ключом сабчарта, просто отбрасываются — без warning, без ошибки. Поймали только диффом отрендеренных лимитов. Правило: проверяйте, что оверрайд доехал, через `helm template | grep`, никогда не предполагайте.
>
> **`MaxRAM` и `memoryMi` связаны жёстко.** `MaxRAM` — это байты, вписанные руками, и они обязаны совпадать с лимитом контейнера. Поменяли одно без другого — JVM считает heap от лимита, которого у контейнера нет, и вы получаете ровно тот же OOMKill. Захотите вернуться к 1024 MiB — в том же коммите ставьте `MaxRAM=1073741824`.

Для справки, реальное потребление на простаивающем кластере против лимита 2048 MiB: connectivity 751Mi, thingssearch 684Mi, policies 486Mi, things 537Mi, gateway 456Mi. Итого нода занята на 4%. Запас взят не «на всякий случай», а под реальную нагрузку двойников.

## Есть ещё одна правка — про Grafana

`grafana.initChownData.enabled: false`. Она не про ARM и проявляется не при установке, а при **любом апгрейде после первой установки**, поэтому живёт в гайде [04](04%20–%20Grafana-плагины.md) вместе с остальной историей про Grafana.

## Если надо начать с нуля

`helm uninstall` оставляет за собой два класса ресурсов, и оба надо убирать руками:

```bash
helm uninstall opentwins -n opentwins
#   -> "These resources were kept due to the resource policy: [PersistentVolumeClaim] opentwins-influxdb2"
kubectl delete pvc --all -n opentwins     # включая тот самый PVC influxdb
kubectl delete job --all -n opentwins     # post-install hook переживает uninstall
kubectl delete pod --all -n opentwins --force --grace-period=0
```

Удалять PVC — осознанная часть чистого старта, а не грубость: InfluxDB уже отработала одноразовый bootstrap админа/бакета/токена на этом томе, и переустановка поверх инициализированного тома — классический источник загадочных ошибок на втором запуске.
